## 改了什么

`BacktestEngine.run()` 里这一行：

```python
# 旧
adj_weights = self._liq.apply(weights, adv_usd_df, self.initial_capital).to_numpy()
```

换成与执行层**同一份原语**的逐日撮合：

```python
# 新
cap_trade_mat = adv_usd * self.params.max_participation_pct / self.initial_capital
prev_filled = np.zeros(N)
for t in range(T):
    fr = simulate_partial_fills(prev_filled, tgt_arr[t], cap_trade_mat[t],
                                max_net=self.max_net)
    adj_weights[t] = fr.filled_w
    prev_filled = fr.filled_w
```

### 旧实现错在哪（两处，不是一处）

**① 口径错：裁的是持仓，而流动性约束的是成交量。**
`LiquidityConstraint.apply` 对整个 T×N **目标持仓**矩阵做 water-filling。
但 ADV 限制的是「今天能成交多少」。一只昨天已经持有 0.5、今天目标还是 0.5 的票
**根本不需要交易**，却照样被 ADV 上限削掉持仓。

**② 会再分配：A 买不到就多买 B。**
water-filling 把被削掉的额度摊给其他票：`[0.9, -0.1]` 落账成 `[0.01, -0.99]` ——
10% 的对冲腿变成 99% 的方向性空头。券商不会这么干。
（构建层用 water-filling 是对的：容量不足就换个票装，产出的是**新目标**并要重新过风控。
执行层不行 —— 用户决定 #1。）

执行层已于 2026-09-18/19 改为 `simulate_partial_fills`，回测一直没动，
于是两个引擎在限流场景下语义分家。原有的 `test_replay_matches_backtest_engine`
用的是成交量充足的数据（上限不绑定），**看不见**这个分叉。

### 新语义是路径依赖的

今天成不了的量既不会凭空消失，也不会被摊给别人，而是**留到以后接着成交**。
持仓向目标逐日逼近，而不是一步到位或被永久削平。

## 差异怎么解释

**只有限流真正绑定时才有差异**，这正是预期：改的是"流动性不足时怎么办"，
不绑定时两种算法本就该给同一个答案。两档不绑定场景**逐位相同**是重要的对照 ——
它证明改动打在点子上，不是无差别地改了所有东西。

绑定场景的三个变化互相印证，指向同一个机制：

**敞口上去了（0.11 → 0.55）。** 旧实现把**持仓**硬压在 ADV 上限附近，于是无论
持有多久，敞口永远上不去。新实现限制的是**每天的成交量**，持仓可以跨日累积 ——
第一天买不到的，第二天接着买。这才是真实世界的样子：流动性差不等于永远只能持有一点点，
而是**建仓慢**。

**换手上去了（3.7 → 12.9）。** 旧实现把目标削得极平，日间目标变动也跟着被削平，
于是几乎不换手。新实现真的在逐日调仓。

**收益变差了（-0.05% → -2.88%）。** 这是前两条的直接后果：真的持有了仓位，
就真的承担了盈亏；真的换手了，就真的付了成本。

**方向是"变差"，这一点很重要。** 旧实现在流动性差的标的上**同时低估了敞口和成本**，
让一个本该"慢慢建仓、付不少成本"的策略看起来像"几乎没持仓、也几乎没亏"。
那是**对自己有利的偏差** —— 回测显示无害，实盘才发现既有敞口又有成本。
修正之后回测更难看，但更接近能兑现的东西。

## 谁受影响

- **生产日循环**：不受影响。`daily_trading_loop` 走的是 `PaperBroker`，
  那一侧 2026-09-18/19 就已经是新语义。
- **历史回测数字**：**流动性受限的标的/时段上会变差**。此前存档的回测结论，
  凡是涉及小市值、低成交量、或大 AUM 相对标的容量偏大的，都应当按新引擎重跑。
- **上限不绑定的回测**：逐位不变，无需重跑。

## 2026-10-18 补充：两边一致，但两边一起错了一处（外部审查 F10）

两套引擎都把持仓按**权重**保存，调仓时直接拿**昨日权重**与今日目标做差 —— 没有先按今天的价格变动
把它漂移成调仓前权重。审查的 R6：50/50 两只票、A 涨 10%，调仓前其实是 52.38% / 47.62%，
系统仍当 50/50，回到 50/50 的成交量与成本都记成 0。上面那条 1e-9 的对账测不出它：两边犯的是同一个错。

修复：共用原语 `transaction_cost.drift_weights`（w·(1+r)/(1+Σw·r)），两套引擎都先漂移再撮合；
成交、换手、成本都从漂移后算。正确性用**现金 + 股数**的手算账本对（`test_accounting_1018.py`），
两边一致性仍由原来的对账守着。

**对历史数字的影响**：换手与交易成本**上升**（价格越波动、调仓越频繁，升得越多），净收益相应下降；
毛收益不变（毛收益本来就是用昨仓 × 今日涨跌算的）。单边换手现在可以略超 1（多空两腿各自涨跌后，
调仓前的总敞口可能超过 1）。此前存档的回测与 paper 账本的成本口径与此不同，比较时要按新引擎重跑。

### 2026-10-19 补充：成交额与费用的美元基准（复审 N08）

漂移修好之后还剩一处单位错误：漂移后的权重是相对**调仓前市值**的，成交额、费用、ADV 成交上限却仍按**期初权益**
换成美元。A/B 各 50%、A 涨 10% 调回 50/50：调仓前市值 10,500，两腿各成交 250，100 bps 应为 5 美元，记成了 4.76。
两套引擎一起改：成交额 / 成本 / ADV 上限用调仓前市值，当天净收益按期初权益归一；回测把撮合并进逐日净值循环
（ADV 上限依赖当天的权益）。手算对账见 `tests/integration/test_review_1019.py`。对历史数字的影响：上涨后调仓的
成本略升、下跌后略降，量级是"当日涨跌幅 × 成本"。

### 2026-10-19 补充（二）：成交后净值归一 —— 独立参考账本查出的共同偏差（复审 N08-b）

复审原话："回测和 paper 一起改过且彼此相等，仍不能证明经济记账正确。"两套引擎互相对账只证明实现一致。
`tests/unit/backtest_engine/test_reference_ledger_1019.py` 写了一份**不用权重**的参考账本：持有股数、现金，
每天按收盘价估值、按目标调股数，成交受日成交量上限（部分成交），费用按成交额从现金扣，空头按昨收市值收借券费。
场景覆盖涨跌、现金、空头、费用、借券、部分成交、中途换仓。

**它先失败了**：两套引擎每天偏约"费用率 × 当日收益率"。原因是费用与借券从现金里扣，持仓市值不变、净值变小 ——
同样的股数占成交后净值的比例**略大**；引擎却把成交那一刻的权重原样带进第二天，第二天的毛收益按略小的仓位算。
两套一起偏，所以互相对账看不出。

修法（两套同时）：第二天估值用 `成交权重 × 调仓前市值 / 成交后净值`。改后两套都对到参考账本 rel 1e-9。
对外的口径分开写清：

| 量 | 口径 |
|---|---|
| PaperBroker `paper_fills.filled_weight`、BacktestEngine `result.positions` | 成交那一刻的权重（相对**调仓前市值**；与目标、风控上限、成交量上限同口径） |
| PaperBroker `paper_positions`（续跑读的昨仓） | 同一笔持仓相对**成交后净值**的权重（第二天估值用） |

12 条按旧口径写的断言随之改正，其中 `test_review_1019` 的费用期望 4.95 → 5.00 是上一轮我自己写错的：
第一天的费用从现金扣，两腿市值仍各 5,000，第二天调仓前市值 10,400，成交 500 × 100 bps = 5.00。
