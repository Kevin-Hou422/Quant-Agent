> 约定：每条 = 症状 → 结论 → 防护。越具体越好，不为凑字数。新经验**追加**到对应主题下，注明日期。

## A. 测试绿 ≠ 系统能跑（最重要）

**2026-08-20** — 一次真实启动前后端的 E2E 验证，在 448 项测试全绿的情况下，仍查出 3 个真实 bug。
原因：测试要么 mock 数据、要么用合成/缓存数据，**结构性地绕开了真实运行路径**（真实 provider
拉取、真实面板的列名、真实退市股票）。

- **结论**：里程碑收尾前，**必须真实跑一遍前后端 + 真实数据**，不能只看测试全绿。
- **防护**：凡涉及"真实数据加载 / 实时 / 摄取 / 成交"的改动，收尾时手动跑一次真实 E2E
  （启动 uvicorn + vite，打真实端点，肉眼核对金融数字是否自洽）。

## B. 安全门不要 fail-open（静默放行）

**2026-08-20** — `check_dataset_health` 内部 `except Exception: return None`，而调用方把 `None`
当"满分通过"。结果健康门崩溃后**一直静默放行**，"拒绝坏数据"（A2）形同虚设，且测试照样绿。

- **结论**：安全/质量门一旦异常，**宁可 fail-closed（拒绝）也不要 fail-open（放行）**；
  宽泛 `except` 里返回"中性/通过值"= 把保护悄悄关掉。
- **防护**：安全门的异常至少 `logger.error`；**写一个断言"坏数据真的被拒"的测试**，而不只是
  "好数据通过"。

## C. 相对导入深度 & 真实路径只在运行时暴露

**2026-08-20** — `dataset_registry.py` 里 `_fetch_yfinance/akshare/ccxt` 导入写错
（`..yahoo_provider` 应为 `.yahoo_provider`；akshare/ccxt 少了 `.providers.`），**所有真实数据
加载都 500**，但因为测试不走真实拉取，没人发现。

- **结论**：`.` vs `..`、子包前缀（`.providers.`）这类相对导入错误，**只在真正执行那条路径时才炸**。
- **防护**：改动"按 provider 分发"的懒加载导入后，直接跑一次真实加载（或 `python -c` 导入那几个函数）。

## D. pandas 面板处理的两个坑

**2026-08-20**
- **列名别按假设的 `level_0/level_1` 重命名**：`df.stack().reset_index()` 的列名取决于索引名
  （yfinance 的行索引叫 `Date`，不是 `level_0`）→ 重命名漏改 → 下游 `KeyError`。
  **按位置赋值**：`long_df.columns = ["timestamp","ticker","close"]`。
- **`stack(dropna=...)` 在 pandas 2.2+ 已废弃/报错**：保留 NA 用 `stack(future_stack=True)`
  （本项目 `pit_store.py`、健康检查处各踩过一次）。

## E. 硬编码 ticker универс会随时间腐坏

**2026-08-20** — SQ(→XYZ)、ABC(→COR)、DFS/PXD(被收购) 等退市/更名后，yfinance 返回**全 NaN 列**，
静默污染所有截面算子（rank/zscore/neutralize）。

- **结论**：硬编码股票池会因并购/更名而出现死列；全 NaN 列不报错但破坏截面计算。
- **防护**：定期扫描各数据集的死列（`close.isna().mean() > 0.95`）；健康门（B 修好后）也能兜住。
  注意：删死列会引入幸存者偏差——但它们本就无数据、删除只是止损，历史幸存者偏差是已知的 F3 遗留。

## F. "机器精度"对账多半是合成数据下的数字

**2026-08-20** — PaperBroker↔回测对账在合成数据下 2.2e-16，但在**真实数据**下是 5.8e-5
（因为真实数据里 ADV 流动性约束会**真的 binding**，两条代码路径的处理有微小差异）。5.8e-5 累计
/501 天在容差内、金融上可忽略，但要知道它不是 2.2e-16。

- **结论**：号称"机器精度"的对账，往往是约束不 binding 的合成数据下才成立。
- **防护**：容差断言要在**约束真的生效的真实数据**上验证；报告数字时标清是合成还是真实口径。

## G. APScheduler 的 CronTrigger 默认用本地时区，不是 scheduler 的时区

**2026-08-22** — `BackgroundScheduler(timezone="UTC")` + `CronTrigger(hour=21)`，实际 next_run 却是
`21:00+08:00`（本地）。因为 **`CronTrigger` 在构造时就把本地时区烘进去了**，不会继承 scheduler
的 timezone。后果：本该"美股收盘后（21:00 UTC）"跑的任务，在本地 21:00（=13:00 UTC=美股早上）就跑了，
当天收盘数据还不存在。**只有真跑起来看 next_run 才会发现**（单测只查 job 是否注册，不查时区）。

- **结论**：APScheduler 的 `CronTrigger`/`IntervalTrigger` **必须显式传 `timezone=`**，别指望 scheduler
  的 timezone 生效。
- **防护**：每个 trigger 显式 `CronTrigger(..., timezone=timezone)`；启动后断言/核对 `next_run` 的
  时区偏移是否为预期（+00:00）。

## H. 部署 .env 不得泄漏进测试

**2026-08-22** — 为真实运行在 `backend/.env` 里设了 `ENABLE_SCHEDULER/PAPER_TRADING/DISCOVERY=true`。
测试也从 `backend/` 跑 → 读到同一 `.env` → **session 级 `TestClient` 的 lifespan 启动了真实调度器**
（起后台线程 + 单例 `_scheduler` 全程 running），导致 `test_status_reflects_running_state` 的前置
`running is False` 失败。全量跑挂、单独跑过（因为单独跑没有别的 test_client 触发 lifespan）。

- **结论**：测试结果**必须与部署配置无关**；部署用的运行开关（enable_*）会经共享 `.env` 泄漏进测试。
- **防护**：conftest 加 **autouse session fixture 强制 `settings.enable_* = False`**（已加
  `_hermetic_run_flags`）；更广义地，开发/测试与运行实例**别共用同一工作目录/.env**（本仓库已踩过多次
  cwd 共用坑：scheduler_jobs.db 竞争、.env 泄漏）。

## I. 把 held-out 集喂进选择目标 = 它就不再是样本外了

**2026-08-24**（外部评估指出，Phase S.1 修）— GP 适应度是
`fitness = sharpe_oos − …`，即**直接按 OOS Sharpe 择优**。跑 100+ 候选全按 OOS 排序 →
**OOS 段被彻底挖掘，退化为第二个样本内**；后面的 WalkForward/DSR 在被挖过的同一段上"验证"，
沦为**循环论证**。看起来很严，实际零信息。而且 README 声称"immutable 三段切割"，代码里发现/验证
路径其实是两段——**文档-代码不符，且不符方向是高估**。

- **结论**：**任何进入选择/优化目标的数据段，都不再是样本外。** 真 held-out 必须对**整个搜索过程
  不可见**，只在最后汇报一次。
- **防护**：三段切割 IS/Validate/Test——GP 只在 **Validate** 上选择，**Test 全程不可见**（已加
  `_partition_three_way` 到发现路径 + 赢家在 Test 上汇报 `test_sharpe`）；更进一步，持久化**跨会话
  累计 trial 数**喂给 DSR/PBO（Phase S.3），否则多重检验膨胀被系统性低估。

## J. 财务关键参数不能是代码里的隐藏默认

**2026-08-25**（用户发现）— PM 用 `paper_aum`、`PaperBroker` 用自带 `initial_capital=1M`，**两个"资金规模"
各说各话**；且用户从没设过 AUM，系统悄悄按 $1M 算持仓。更广地一查：**成本模型**（`min_ticket=$1`、
`fixed_bps=5`、机构口径）、**策略结构**（永远美元中性**多空**、假设可自由做空）、**调仓频率**（隐含每日
全额）——全是代码默认，悄悄假设了"能自由做空 + 机构级低成本"。**这些直接决定"能不能赚钱"的答案**：
同一因子在 $10k 散户口径 vs $1M 机构口径下，结论可能相反。

- **结论**：当系统的目的就是"**验证在特定资金/成本下能否赚钱**"时，**资金规模、成本口径、可交易性约束
  （能否做空）、调仓频率**这些**直接决定答案的输入，绝不能是代码里的隐藏默认**——必须①显式（用户设）、
  ②由真实情景推导（有分析、非拍脑袋）、③**单一来源**（不重复、不分叉）。
- **防护**：把每个财务/行为参数分三层区别对待——
  - **T1 现实事实**（AUM、账户类型、allow_short、券商费率）→ **显式配置**（用户声明，非隐藏默认）。
  - **T2 数据推导的估计**（价差、冲击、可做空性、调仓带）→ **系统自己从免费数据每次重算**
    （`TradingContext`：Corwin-Schultz 估价差等），明确是"估计"，不冻结成常量。
  - **T3 只有交易当时才知道的**（真实盘口价差、借券 locate/费、成交价、买入力、停牌）→
    **绝不写字面值**，一律走 provider 接口；仿真背 T2 估计、实盘背券商实时 API，**同接口切换**。
  - AUM 只走 `paper_aum` 一条线贯穿 PM 与 broker（已修）；**研究与执行必须用同一个权威数据源**
    （否则 train/serve skew，验证白做）。任何"机构默认"进入"散户小资金"目标前，先问"它在目标情景下还成立吗"。

## K. 完成 ≠ 接进主线（本轮最重要的复盘）

**2026-08-30**（用户一针见血）— 建了 PM.S1/S2（策略门/边际准入）、PM.5（风控门），每个都带单测且全绿，
但**都没接进 `run_portfolio` 主线**——是"带单测的库"，不是"生效的功能"。用户说"很多已完成的部分和没做一样"。

- **结论**：一个功能"完成"的标准 = **在运行时主线上被真正调用 + 端到端验证过**，不是"单测绿"。
  孤立的带单测模块 = 没做。
- **防护**：每做一个模块，**同一批次就接进主线 + 写一个"主线确实调用了它"的集成测试**
  （如 `test_phase_pm_wiring.py` 断言 `run_portfolio` 返回里有该门的产物 `selection/strategy_verdict/risk_report`）；
  里程碑收尾用 **AST 可达性从运行入口扫一遍**，"有价值但不可达"的模块要么接线要么删；再跑真 E2E 串起所有存活组件（§A）。

## L. 删死代码的方法论（可达性 / 同名 / 实测）

**2026-08-30** — 清 ~2740 行死代码时踩了三个坑：① 静态可达性若不建模**包 `__init__` 执行 + re-export**，
会把"经 __init__ 被加载"的模块误判为孤儿；② 死壳与活模块**同名**（`portfolio_constructor` 活在
`backtest_engine`、死壳在 `portfolio_engine`），**按名字删会误杀活的**（验证脚本就误删过）；③ 按**符号名**
grep 会把不同模块的同名函数混为一谈（`generate_random_alpha` 活在 `gp_engine`、死在 `generator`）。

- **结论**："删了无影响"不能靠单一 grep 断言。
- **防护**：删前**四步确认**——① git 历史查来历+为何存在；② 确认有同功能替代且在主线；③ 追**实际 import
  来源**（非符号名）证明活代码不用它；④ 前端依赖（前端只经 API，查端点 handler 不碰它）。最后**实测**：
  备份 → 真删+清 __init__ re-export → `import app.main` + 全量测试 → 还原。**删除按精确路径，绝不按 basename。**

## M. 换数据源的收尾 + 前端"能跑"≠"类型门过"

**2026-08-30**
- **换数据源不只是换 fetch**：符号格式会不同（yfinance `BRK-B` vs moomoo `US.BRK.B`，实测确认）、
  缓存键要含 `price_source`（否则换源返旧缓存）、新部署配置（`PRICE_SOURCE=moomoo`）要在 conftest
  强制回退（否则测试打真网关 + 烧行情额度，再犯 §H）。
- **前端"能构建"≠"类型门过"**：`vite build` 不做类型检查照样产出可运行包；`npm run build` 的 `tsc -b`
  是独立严格门，且会把**测试文件**的类型错误（vitest 全局 `afterEach`、未用 import）带进生产构建门。
  **防护**：生产 tsconfig 排除 `src/__tests__`（测试交 vitest 跑）、`vite.config` 用 `defineConfig from 'vitest/config'`；
  区分"app 能跑"和"类型门过"。

## O. 合成测试数据的 H/L 会让价差估计荒谬 → 成本模型把好策略判死

**2026-09-02**（真跑 mock 全流程时查出）— 测试夹具普遍写 `high=close*1.01, low=close*0.99`（**每天固定 ±1%**）。
Corwin-Schultz 从 H/L 反推价差，对这种"恒定日内区间"会估出 **~54 bps** 的价差（真实美股大盘 2~10 bps）。
后果：一个**真有 alpha** 的因子（零成本下 OOS Sharpe **+2.06**）被成本压成 **−2.16**，**边际准入把它误拒**。
换成真实感随机振幅（~0.6%）后估价差 8.5 bps，策略回到 **+1.39**。

- **结论**：凡是**会走成本/价差推导路径**的测试，合成数据的 **H/L 必须是随机的、量级真实的日内振幅**；
  固定百分比区间会让 Corwin-Schultz 输出荒谬价差，**把成本模型变成"杀死一切策略"的黑洞**。
- **防护**：合成面板一律 `amp = |N(0, 0.006)|; high = close*(1+amp); low = close*(1-amp)`；
  review 成本相关结论前先看一眼 `median_spread_bps` 是否在 2~15bps 的常识区间（FE-TR 面板已展示该值）。

## P. 昂贵推导别放进 O(n²) 循环——先量再改

**2026-09-02** — 把"成本参数"与"无交易带"改成由数据推导（各跑一次 Corwin-Schultz 全 panel）后，
它们落在 `marginal_factor_selection` 的 **O(n²) 贪心循环**和 PBO 的按因子循环里被反复重算，
全量回归从 **~5 分钟 → 1 小时 40 分**。而我用小面板做的微基准**没有暴露**这一点（单次调用反而更快）。

- **结论**：把某个计算"从常量改成按数据推导"时，必须查它被**调用多少次**——单次耗时不代表总耗时；
  微基准要在**真实调用图**（含 O(n²) 的选择/搜索循环）下做，否则会误判。
- **防护**：这类推导做**记忆化**（按 dataset 身份+AUM 缓存，见 `strategy_gate._DERIVE_CACHE`）；
  回归耗时本身当指标看——**跑得比平时久一个数量级，就是性能回退的信号**。

## Q. 活的 SQLite 绝不能放在云同步目录；备份要"一致性快照"而非复制文件

**2026-09-05** — 整个项目（含 `alphas.db`、`pit_store/`）一直放在 **OneDrive 同步目录**里，OneDrive 常驻运行。

- **为什么危险**：WAL 模式下 `.db` / `.db-wal` / `.db-shm` **三个文件必须互相一致**，而云盘会**分别、异步**
  上传 → 同步/恢复回来可能是不一致的三件套（损坏）；上传占用文件还会引发 `database is locked`；
  Files On-Demand 还可能把文件"脱机化"成占位符，定时任务访问时卡住。**它给的是"有备份"的错觉，
  实际是逐文件碎片同步，不是可恢复的快照。**
- **结论**：**活数据放本地非同步盘**（`%LOCALAPPDATA%`），**代码留在云盘/git 无所谓**（代码可再生）；
  **备份用一致性快照**——SQLite 用 `VACUUM INTO`（读事务内产出完整单文件，能带上 WAL 里尚未 checkpoint
  的写入），**绝不 `copy` 活库**；快照是静态文件，**放进云盘才是安全的异地副本**。
- **额外防护**：快照后立刻 `PRAGMA integrity_check`，**坏备份比没备份更危险**（让人误以为有救）；
  备份"什么都没备到"时必须 `ok=False`（本次实现最初就漏了这点，被测试抓出来）。
- **本系统特别之处**：**前向数据不可再生**——券商只给历史 K 线，"前向"的身份来自你当时就记下了。
  丢一次就是几个月，TR.4 的 →ACTIVE 门直接归零重来。

## R. 反复"只测局部"的根因：验证由与实现同一个心智模型生成

**2026-09-05**（外部审计打脸后复盘）— 同一会话内**同一失效模式出现 4 次**，且都由用户而非我发现：

| 事件 | 我测的（局部） | 漏掉的（全局） |
|------|----------------|----------------|
| 删死代码 | grep "0 引用" | 包 `__init__` re-export 耦合、同名活模块（按名字删会误杀） |
| 报 PM.S1/S2/PM.5 "完成" | 单测全绿 | **没接主线 = 等于没做**（写完 §K 后又对 `grade_paper_entry` 重犯一次） |
| 报"无性能回退" | 单次调用微基准（反而更快） | O(n²) 调用图里 → 全量回归 5 分钟变 **100 分钟** |
| 报 E2E "10/10 组件通过" | 调度器主线 | **从没打过 `/api/chat`** → 聊天把合成随机数据包装成 Sharpe/OOS 研究结论 |

- **根因（不是"不够仔细"）**：**验证用例是由和实现同一个心智模型生成的**，因此它**结构性地看不见同一个盲区**——
  我没想到的路径，我也不会去测。三个放大因素：
  ① **把通过率当覆盖率**：`10/10 passed` 只证明"我跑过的没错"，**不证明"我没跑的没错"**，但它长得像完整性；
  ② **按"改动范围"定验证范围，而风险边界是"断言范围"**：改了 `run_portfolio` 就只测它，可断言却是"系统能用"；
  ③ **绿灯终止搜索**：局部验证秒级变绿且给正反馈，全局验证慢且常带来坏消息，梯度天然推向前者。
- **防护（机制，不是"下次更仔细"）**：
  1. **写不变量，不只写用例**——用例抓实例，不变量抓类别。本仓库已固化：
     「生产路径不得静默回退合成数据」「有价值模块必须从入口可达」「门评估的账本==实际交易的账本」。
  2. **入口清单当一等资产**：枚举所有用户入口（API 路由 / 调度 job / CLI），E2E **逐个覆盖或显式列为未覆盖**。
  3. **报结论必须同时报范围与未覆盖**：不说"10/10 通过"，要说"10/10 通过；**未覆盖：chat、GP API**"。
     **留白正是出错的地方**——强制列出未覆盖会逼自己每次重算范围。
  4. **验证后追问一句**："如果这个结论是错的，最可能错在哪个我没看的地方？"然后去看那里。
- **附带教训**：让正确性依赖用户的怀疑，本身就是分工错误；把上面 1、2 搬进测试，才是把职责搬回代码里。

## S. 教训不落成"会失败的检查"，复发率≈100%（本轮全量测试审计的结论）

**触发**：用户问"这么多次全量审计为什么发现不了真问题，dev lesson 到底有没有用"。逐条量化后：
18 条教训里只有 5 个测试文件引用过 DEV_LESSONS，其余以散文躺在 md 里；**凡是没变成检查的都复发了**——
§K 写完当天在**参数层**复发（`port_vol_ann`），§R 写完当天在 **SSE 路径**复发，
而且 §R 复发的同一个文件里还藏着第三处同类漏洞（`_tools.tool_run_gp_optimization` 的 per-run 静默降级）。

### S.1 三个机制性盲区（不是"不够仔细"）

| 盲区 | 具体形态 | 实测后果 |
|------|----------|----------|
| **断言写成了不会失败的形状** | `assert status_code in (200,400,422,500)`（恒真）、`if status_code==200:` 包住断言、`try/except Exception: pass` 包住整个测试体、`assert ... or True` | `/api/backtest/walk_forward` 合成路径**从来 100% 返回 500**，测试一直绿；`test_api_workflow.py` 全部 8 个用例的载荷违反 `ge=` 约束 → 端点**从未被调用过**；`test_backtest_edge_cases.py` 的 `_run_backtest` 少传一个必填参数，**每次都 TypeError**，被 `except: pass` 吃掉 |
| **测试环境 ≠ 部署环境（我自己造的）** | `conftest._hermetic_run_flags` 覆盖 `settings`（不打网络、不起调度器） | **没有任何测试跑在发布配置下** → "函数写对了但默认值没打开"整类 bug 结构性不可见。门控函数单测全绿，线上四个硬门默认全不拦 |
| **审计的检索单位错了** | 历次审计问的是"Phase X 做完没 / 模块接线没" | 真问题全在**比模块细**（一个参数、一个默认值、docstring 里的字符串、一处 `except: pass`）或**比模块粗**（横切属性：结果是否带来源、谁能调这个端点）的层级，按模块扫两头都看不见 |

### S.2 单测能过、系统仍错的典型：`ind_neutralize`

`tests/test_dsl_engine.py::test_ind_neutralize` 直接调 `fast_ops.ind_neutralize(x, groups)` —— **一直通过**。
但走 parser→executor 的真实路径上，parser 把分组存进 `params["groups_node"]`，
`CrossSectionalNode._compute` 读的却是 `params["groups"]` → 恒为 `None` → 退化成 `cs_zscore`。
**行业中性从未生效**，且给不给 `sector` 输出逐位相同。兄弟算子 `sector_neutral` 读 `dataset["groups"]`，正常。
> 单测测的是**函数**，bug 在**接线**。这就是 §R 的最纯形态。判别性用例（"给参数与不给参数的输出必须不同"）
> 一行就能抓住它，而"输出均值≈0"这种弱断言恰好被退化版满足。

### S.3 规则（已落成 `tests/test_lessons_enforced.py`，缺一条即红）

1. **禁恒真断言**：不得容忍 `500`（`502/503` 是设计内的上游失败，允许）；不得把断言藏在 `if status_code` 里；
   不得整体 `except: pass`；不得 `assert True` / `assert x or True`。
2. **禁静默降级**：门控/风控模块的 `except` 必须记录或抛出；数据加载失败切换数据源时必须**同步更新来源标识**。
3. **参数级可达性**：影响资金/风险的关键形参，必须有真实调用点传值（§K 从模块粒度下沉到参数粒度）。
4. **提示词里的标识符必须真实存在**：LLM 可见的数据集名要在注册表里查得到（否则 LLM 照着调用→失败→走降级）。
5. **夹具真实性**：禁止 `high=close*1.01` 这种固定 ±1% 日内区间（§O）。
6. **必须有跑在发布配置下的测试**：`tests/test_production_defaults.py`，标记 `production_defaults`。
   门控默认值写成显式快照表，任何变动都得有人改这张表 → 在 review 里被看见。
7. **每条教训都必须有对应检查**：`test_every_lesson_has_an_enforced_check` 扫 DEV_LESSONS 的标题，
   缺检查又不在 `EXEMPT`（须写明为何无法自动化）即失败。**这条是元规则，防止本文件重新退化成散文。**

- **判据**：写完一条教训问自己——"它能让哪个测试变红？"答不上来，就还没写完。

## T. "算子存在" ≠ "算子接线正确"：参数在 AST 里，消费方在别处找

**触发**（B-7）：`ind_neutralize(x, 'sector')` 的**行业中性从未生效**。
parser 把第二参存进 `params["groups_node"]`（一个 AST 节点），
`CrossSectionalNode._compute` 读的却是 `params["groups"]` —— 永远 `None`，
`fast_ops.ind_neutralize` 遂静默退化为 `cs_zscore`。
判据一行就能测出：**给 sector 与不给 sector，输出逐位相同**。

为什么长期没被发现：
- `tests/test_dsl_engine.py::test_ind_neutralize` 直接调 `fast_ops.ind_neutralize(x, groups)` ——
  **绕过了出 bug 的那段接线**，函数本身没错，所以一直绿；
- 集成侧断言写的是"全截面均值 < 0.5"，而 `cs_zscore` 的全截面均值恒为 0 ——
  **退化版恰好满足弱断言**。

同一次排查还发现 `GroupNode._compute` 在分组字段缺失时**凭空捏造** `np.arange(N) % 10`，
按 `i % 10` 做"分组中性化"。这比退化成 `cs_zscore` 更坏：`cs_zscore` 至少是个自洽运算，
而假分组产出的是**看起来像分组结果的无意义数字**。
（`dsl_executor.py` 的注释声称该假分组"已被移除" —— 只从那一处移除了。）

### 规则
1. **参数从 AST 到消费方要有一条被测的通路**。存参数的键名与读参数的键名必须由测试锁定，
   不能靠"看起来对"。
2. **判别性断言 > 数值断言**：测"带参数与不带参数的结果必须不同"，
   比测"结果均值≈0"强得多 —— 后者常被退化实现意外满足。
3. **缺输入时宁可报错，也不要编造输入**。自动生成分组/填充默认值，
   会把"没数据"变成"有数据但全错"，且看不出来。降级必须告警（§B/§F 同理）。
4. 单测覆盖了函数**不代表**覆盖了调用它的那条路径 —— 这是 §R 在算子层的具体形态。

## U. 兜底要朝**保守**一侧倒；"读不到配置"不等于"按最宽松处理"

**触发**（审计 #9 整改）：全库 131 处"既不记录也不抛出"的 `except` 里，最危险的不是
数量，而是**兜底方向反了**——失败时系统自动滑向更宽松、更冒险的一侧：

| 位置 | 读不到配置时的兜底 | 实际含义 |
|------|------------------|----------|
| `manager.py` | `long_only = False` | **允许做空**（现金账户会构造出根本无法成交的空头腿） |
| `discovery_engine.py` | `mode = "leak"` | 用**松**的因子门 —— 而它自己的 docstring 写着"fail-closed：出错视为不通过" |
| `validation_gate.py` / `strategy_gate.py` | `n_trials = 1` | 宣称"只试过一个策略" → Deflated Sharpe 不做多重检验校正 → **门变松** |
| `trading_context/providers.positions()` | `return {}` | "我什么都没持有" → 下游把全部权益当可用买入力 → **按满额重新建仓**，等于凭空加杠杆 |

四处的共同点：**异常发生时，系统做出的是"更容易通过 / 更容易下单"的选择**。
这比崩溃危险得多——崩溃会被发现，而"悄悄放宽"看起来一切正常。

### 规则
1. **兜底必须朝保守一侧**：读不到"是否允许做空"→ 假定不允许；读不到门控模式 → 用严门；
   读不到试验次数 → 不要假装只试过一次。
2. **表示"没有"的返回值要格外小心**：`{}` / `[]` / `0` 在业务上常常不是"未知"而是
   一个**具体且危险的断言**（空仓 = 满额可用买入力）。宁可抛错让调用方决定。
3. **兜底与文档必须一致**：`discovery_engine` 的 docstring 与代码方向相反，
   说明写文档和写兜底的不是同一时刻的思路 —— 有 docstring 声明纪律的地方，
   要专门检查代码是否真的照做。
4. **区分"判定结果"与"检查器故障"**：`check_dataset_health` 把自己 `raise` 的
   `ValueError` 又用 `except Exception` 吃掉，导致 fail-closed 开关**从未生效**。
   有意抛出的业务异常必须用**专用类型**，并在通用兜底前显式放行。
5. **数量用棘轮管，不靠自觉**：`test_silent_except_count_does_not_grow` 记录当前
   静默 except 总数，只许降不许升；降了必须同步下调预算，防止悄悄回潮。

- **判据**：看到一处 `except: <默认值>` 时问——"如果这个默认值是错的，
  系统会变得更谨慎还是更冒险？"答案是后者，就必须改方向或改成抛错。
